# Future ESP32 / Blynk integration contract

No firmware or bridge is included. This contract lets a later trusted integration write data without changing the React UI.

1. An authenticated bridge binds a device to an approved caregiver UID. Validate that binding on every operation; do not trust a client-supplied UID. Keep Firebase Admin credentials on a trusted server only. Blynk can transport device data to the bridge; normal web CRUD continues to use Firebase independently.
2. Read `accounts/{uid}/catalog/schedules` and the associated medicines. Deliver active schedules, schedule IDs, times, compartment IDs, timing windows, revision timestamps and the configured timezone to the device. Revisions let a device detect updated schedules. No dosage fields are generated by the dashboard.
3. The device/bridge determines timing outcomes. Use the scheduled instant through the end of the on-time window for ON_TIME, the following grace period for LATE, and record MISSED after grace expires if no valid access occurred. Later access emits a new POST_MISSED record; it must not overwrite MISSED. Resolve overlapping test windows deterministically and include the selected schedule identity.
4. Write events idempotently with a persistent device ID + boot/session ID + monotonic sequence as the Firebase key. Do not use a fresh push key every time a buffered event is retried. Store the **original occurrence timestamp**, not its later upload time. `syncStatus` may describe buffering/sync; original event identity/type/occurrence must remain intact.
5. Use an atomic multi-location update when an event also creates a corresponding alert, so the browser sees consistent records. Device alerts support `ACTIVE_REMINDER`, `MISSED`, `WRONG_COMPARTMENT`, `LOW_STOCK`, `REFILL_REQUIRED`, `DEVICE_FAULT`, `SENSOR_FAULT`, and `INPUT_FAULT`. Manual stock alerts already derive from medicine inventory and need not be duplicated by the bridge.
6. Maintain heartbeats under `devices/{deviceId}`. Send `connectionStatus`, `lastSeen`, `lastSync`, `cloudStatus`, `pendingOfflineEvents`, `rtcStatus`, and `faultStatus` from actual measurements. Missing fields render as unknown/not reported. Do not copy the dashboard's Firebase network connection into ESP32 online status.
7. Write `compartments/{Mon-A|Mon-B|Tue-A|Tue-B|Wed-A|Wed-B|Thu-A|Thu-B|Fri-A|Fri-B|Sat-A|Sat-B|Sun-A|Sun-B}` with `deviceId`, `status`, and `reportedAt`. These are the 14 physical compartment identifiers. Accepted display concepts include AVAILABLE, ASSIGNED, REMINDER_ACTIVE, OPEN, CLOSED, UNKNOWN and OFFLINE. Configured assignments come from schedules; physical door/reminder state comes from hardware only.
8. Read caregiver notification preferences. MISSED and WRONG_COMPARTMENT are always modeled as eligible categories. A future delivery service must honor `notificationsEnabled`, perform deduplication, and report actual delivery status. This app stores preferences but sends no emails or SMS.

An event record must contain a real occurrence timestamp, scheduled date/time, schedule and medicine identity where applicable, compartment ID, supported event type, access status, alert status, caregiver notification status, sync status, and device ID. Do not create records from this contract; only the trusted device integration may write reported events.

Supported `eventType` values are ON_TIME, LATE, MISSED, POST_MISSED, WRONG_COMPARTMENT, SENSOR_FAULT and INPUT_FAULT. Access, alert, notification and sync fields should use documented bridge enums (for example OPENED/NO_ACCESS; NONE/ALERT_CREATED; NOT_REQUIRED/PENDING/SENT/FAILED/DISABLED; PENDING/SYNCED/ERROR). These are reporting fields, not proof of medication ingestion.

Firebase rules intentionally **deny every browser write** to `events`, `alerts`, `devices`, and `compartments`. Do not loosen them to connect hardware. A future trusted bridge can use Admin SDK after its own device authentication and payload validation, or deploy narrowly scoped device-specific rules/custom claims. Admin SDK bypasses database rules, so validate all fields and invariants there.

Keep stock updates independent. A lid opening must never automatically decrement stock. A later calibrated sensor estimate should have its own provenance and validation before it can replace a manual count.
